## 交付加固（2026-10-19）

目标：把 Demo 从「能跑通」推进到「随时可交付」——真实数据库、真实并发、真实故障注入，发现问题先写复现测试再修复，不隐藏失败。

- **SQLite 并发根因**：Prisma 默认按 CPU 数打开多个 SQLite 连接，多连接同时写同一库会互相等锁并最终抛 `P1008 socket timeout`，表现为并发过账偶发 503。这不是业务规则错误，是连接池与存储引擎模型不匹配。修复：`repositories/db.ts` 统一注入 `connection_limit=1&socket_timeout=30`，写入在客户端串行化，与 SQLite 单写者模型一致。实测 20 路并发写入从「10 成功/10 失败」变为 20/20 成功且账实一致，`enterprise.test.ts` 从 25 秒 4 失败变为 0.8 秒全绿。**不通过降低并发数或弱化断言来规避**。
- **事务重试边界**：对交互式事务（回调形式）加 P1008/P2028/P2034/P2024 指数退避重试（最多 5 次、带抖动）；数组形式 `$transaction([...])` 传入的是已在执行的 Promise，重试会重复提交，因此原样执行。业务拒绝（409/422）绝不重试。
- **测试基础设施**：`supertest@7` 会为 Express app 惰性创建共享 server，并在最后一个在途请求结束时关闭。若两个请求生命周期交错（典型：`agent.patch(...).set('If-Match', await match(...))`），先结束的请求会关掉 server，另一个 dispatch 时 `server.address()` 为 null，抛 `Cannot read properties of null (reading 'address')`。修复：`tests/server.ts` 的 `startTestServer()` 显式 `createServer` + `listen(0)`，生命周期由测试文件控制。**这是测试基础设施缺陷，不是产品缺陷**，因此改测试而不是改业务代码。
- **会话隔离真实缺陷**：旧会话延迟返回的 401 会被全局响应拦截器当作「当前会话失效」，把刚切换登录的新账号踢回登录页。修复：请求发出时记录当时的 CSRF Token（会话标识），响应到达时用 `isCurrentSessionFailure()` 判断该 401 是否属于当前会话，只对当前会话的 401 清登录态。浏览器用例已从红转绿。
- **配置注入**：安全中间件、Cookie 属性原先直接读 `process.env`，导致 `createApp(config)` 注入的配置被忽略、多实例测试互相污染。修复：配置挂到 `app.locals.runtime`，请求期经 `config/context.ts` 读取；`sessionCookie()` 统一 Cookie 属性。新增用例用两个不同来源的 app 实例证明隔离生效。
- **备份/恢复/核对**：备份用 SQLite `VACUUM INTO` 生成事务一致性快照（不直接复制活动库文件，避免拿到写了一半的页）；恢复只写**不存在**的新库、拒绝覆盖、恢复后清除全部 Session；`checkIntegrity()` 覆盖七项账实不变量（库存余额=流水累计、流水前后连续、单据金额=明细合计、订单累计入出库=明细合计、应收应付=结算流水、正式单据↔往来单一一对应、流水来源唯一且匹配类型）。源库核对不过时**拒绝备份**，备份核对不过时**拒绝恢复**。
- **生产配置**：生产强制 HTTPS 来源、显式绝对 SQLite 路径、`TRUST_PROXY` 仅允许 `false|loopback`（禁止 `true`/`1`/`*`，防止伪造转发头绕过来源与限流）；健康/就绪探针允许 HTTP 以适配容器探针。
- 未初始化 Git、未推送、未发布；所有验证在本地真实数据库与真实浏览器完成，不将本地验证等同公网生产验收。

## Phase 3

- 用户“继续下一阶段”授权Phase3，验收后停在Phase3，不提前实现销售或付款。
- 为验收入库闭环，开放库存余额/流水/应付只读页；采购统计留Phase6，付款留Phase5。
- 数量最多100万，单价最多1,000,000,000分（1000万元），行及单总额最多2,000,000,000分（2000万元）。服务端整数计算，数据库触发器再次约束。
- 同订单不允许重复商品；入库仓库固定来源订单；停用商品/分类/供应商/仓库阻止新建或过账。
- SQLite过账先取得写锁，再检查幂等及最新余量；条件更新、唯一键和同事务保证不超入、不重复。冲突/繁忙返回409/503，使用原键重试，不自动猜测结果。
- 前端未确认入库请求按用户+订单保存sessionStorage中的原请求和幂等键，关闭抽屉或刷新仍能重试；明确4xx失败允许修正。
- 采购权限通过独立迁移增量补入现有默认角色；Seed不覆盖权限和密码。演示采购通过Service生成，固定PO-DEMO编号防重复；不为凑数据直接修改库存或应付。
- Windows正在运行API时Prisma DLL不可重新生成，迁移/测试前停止本项目开发服务，验收后恢复；README明确说明。

- 驳回原因使用独立字段，不覆盖业务备注；零额应付直接结清。Prisma重建表会删除触发器，后续迁移需检查并恢复保护，测试固定核对现有14条保护。
